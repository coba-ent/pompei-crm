# Aislamiento y Seguridad Checklist: Conexión Tiendanube vía Application REST del Partner Portal

**Purpose**: Validar, antes de `/speckit-tasks`, que los requisitos de esta spec dejan sin ambigüedad (a)
que ninguna operación de esta conexión nueva pueda tocar `tn_configuracion`, `ClienteTiendanube` ni los
flujos de ventas/stock (specs 017/018/019), y (b) que el manejo de credenciales está completamente
especificado, dado que ambas conexiones operan contra la cuenta real de producción del cliente sin sandbox.
**Created**: 2026-07-31
**Feature**: [spec.md](../spec.md)

**Note**: This checklist is generated by the `/speckit-checklist` command based on feature context and requirements.

## Aislamiento respecto de spec 019

- [x] CHK001 - ¿Está explícitamente especificado que ninguna tabla de esta spec modifica el esquema de
  `tn_configuracion`/`tn_operaciones_log`? [Completeness, Spec §Key Entities]
- [x] CHK002 - ¿Está definido, para cada acción de esta conexión (conectar/verificar/desconectar), qué
  columnas exactas puede leer o escribir, de forma que no haya ambigüedad sobre si podría tocar
  `tn_configuracion`? [Clarity, Spec §FR-008]
- [x] CHK003 - ¿Hay un requisito explícito de que la suite de tests existente de spec 019
  (`ClienteTiendanube`, `TiendanubeOAuthController`) debe seguir pasando sin modificarse tras implementar
  esta spec? [Completeness, Spec §FR-013]
- [x] CHK004 - ¿Está especificado qué pasa con el estado de esta conexión cuando se desconecta la conexión
  MCP existente (y viceversa), de forma consistente en ambos sentidos? [Consistency, Spec §User Story 2]
- [x] CHK005 - ¿Los requisitos distinguen de forma verificable (no sólo narrativa) el historial de esta
  conexión del historial de la conexión MCP, de modo que una consulta futura no pueda confundir a qué
  conexión pertenece una fila? [Measurability, Spec §FR-011] — Resuelto en `/plan`: tabla separada
  `tn_rest_operaciones_log` (`data-model.md`), no columna discriminadora.
- [x] CHK006 - ¿Está explícitamente fuera de alcance que esta conexión sea invocada desde código de specs
  017/018 o desde vinculaciones, de forma que un futuro implementador no la conecte "de paso"? [Boundary,
  Spec §FR-012]

## Manejo seguro de credenciales

- [x] CHK007 - ¿Está especificado que el `access_token` de esta conexión nunca se expone en claro en la
  interfaz, el historial o los logs, para todos los flujos (conexión, verificación, error, desconexión)?
  [Completeness, Spec §FR-006]
- [x] CHK008 - ¿Está definido dónde vive el `client_secret` de la Application (config/entorno) y que nunca
  se persiste en base de datos, evitando ambigüedad sobre si `tn_conexion_rest` debería guardarlo?
  [Clarity, Spec §Assumptions]
- [x] CHK009 - ¿Los requisitos de manejo de error (state inválido, código reusado, `access_denied`)
  especifican que el mensaje mostrado al usuario nunca incluye el `code`, el `access_token` ni el
  `client_secret` crudos? [Completeness, Spec §Edge Cases]
- [x] CHK010 - ¿Está especificado el comportamiento ante la imposibilidad de descifrar el token guardado
  (rotación de clave de aplicación), de forma consistente con el mismo escenario ya cubierto para la
  conexión MCP? [Consistency, Spec §Edge Cases]
- [x] CHK011 - ¿Se documenta explícitamente que el `redirect_uri` fijo del Partner Portal es una superficie
  de riesgo (si alguien lo cambia a una URL no controlada por el CRM, el código de autorización de la
  cuenta real quedaría expuesto a un tercero)? [Gap, Security] — Resuelto: agregado como edge case en
  `spec.md`.
- [x] CHK012 - ¿Está definido qué scopes mínimos se solicitan o aceptan, de forma que la verificación
  (FR-005) no dependa de un scope que la Application podría no tener otorgado? [Clarity, Spec §Assumptions]

## Cobertura de escenarios de falla

- [x] CHK013 - ¿Están definidos requisitos para el caso en que la verificación (`GET /store`) responde con
  éxito HTTP pero con datos incompletos (ej. sin `name`/`original_domain`)? [Gap, Edge Case] — *cubierto
  implícitamente por FR-005 ("si la verificación falla... no queda conectada"), pero la spec no distingue
  explícitamente "falla HTTP" de "200 con payload inesperado". Bajo impacto: research.md/contracts ya fijan
  la forma esperada del payload real.*
- [x] CHK014 - ¿Están definidos los límites de reintento (número acotado) de forma consistente entre el
  flujo de conexión inicial y cualquier verificación posterior? [Consistency, Spec §FR-010]
- [x] CHK015 - ¿Se especifica el comportamiento cuando el usuario presiona "Conectar" en esta conexión
  mientras el flujo de la conexión MCP está en curso (ambos comparten pantalla)? [Coverage, Spec §Edge
  Cases]
